## 2. BLOCKER findings

### B1 — Strategy execution isolation

Reviewer evidence:
- strategyCompiler._loadModuleFromString uses new Module(...)._compile(code), with project node_modules in mod.paths.
- User strategy source executes with ordinary Node privileges, in the main process for PAPER/LIVE and the job worker for backtests.
- Worker loads dotenv and has database access.
- Static validation/scanning is not a security sandbox.

Required plan correction:
- P1-01 defines the strategy trust and isolation boundary; P1-03 defines the capabilities exposed to strategy code.
- Strategy code must not receive ambient process, filesystem, environment, network, database or other users' broker-session access.
- Evaluate process-per-runtime, a genuine isolate with no ambient authority, and trusted single-owner-only operation. Record trade-offs and cost.
- Multi-user LIVE is blocked until the selected isolation model is implemented and security-tested.
- Verify compiler, worker privilege model, strategy save permissions and all execution modes before treating the exact exploit surface as fully established.

### B2 — One authoritative risk-gated order entry path

Reviewer evidence:
- PAPER/LIVE strategy signals flow MarketFeed._feedRuntime -> broker.handle(signal), without calling RiskGateway directly.
- Manual/SocketX commands reportedly flow RiskGateway.submit -> riskEngine.check -> broker.handle.
- Backtests reportedly flow _runSimulation -> broker.execute(), bypassing submit/handle and risk.
- RiskGateway._defaultRiskCheck reportedly allows when broker lacks getEquity and checks only drawdown, flat-exit and same-side conditions.

Author's source verification correction (2026-11-01): BaseBroker.handle is not an unguarded path. engine/core/engine.js _wireSocketX installs BaseBroker.setRiskValidator using SignalProcessingEngine.validateForCommand; BaseBroker.handle calls this validator and fails closed if it is absent or rejects. Therefore MarketFeed's call to broker.handle does receive this validator in the normal engine wiring. The stronger defect is inconsistent/duplicated ownership: RiskGateway.submit pre-checks through SocketXRiskEngine (which delegates to the same SignalProcessingEngine) and then broker.handle repeats the BaseBroker validator, while BacktestDriver.execute is a direct synchronous method and bypasses BaseBroker.handle entirely. SignalProcessingEngine currently checks drawdown, flat exit and same-side/scaling; maxDailyLossLimit is declared but not used. RiskGateway._defaultRiskCheck is the fallback when no risk engine is injected; engine wiring does inject SocketXRiskEngine, so do not present that fallback's missing-method behavior as the normal production path.

SocketX integration also needs correction: engine/core/engine.js imports SocketXServer and sets its static auth verifier, but no SocketXServer instance was found in the inspected engine/server.js or engine/core/engine.js. engine/server.js routes /ws to the broadcaster and /mt5 to the bridge. Confirm whether another entry point instantiates SocketXServer before treating the RiskGateway command path as active in production.

Required plan correction:
- P1-03 names one authoritative order-intent entry point and one owner for risk policy.
- Strategy, manual and automated order sources pass through the approved policy boundary before execution.
- Decide whether backtests use the same risk rules as LIVE/PAPER or a documented simulation policy with parity/divergence tests.
- Define fail-closed behavior when required account/equity/risk data is unavailable.
- Define account-scoped exposure limits; do not assume current RiskGateway is a complete risk engine.
- VERIFY whether BaseBroker.handle adds validation and inspect PAPER broker behavior.

## 3. MAJOR findings

### M1 — Explicit tenant boundary

Reviewer evidence:
- Strategy/report/upload ownership is encoded in scoped identifiers.
- Worker strategy lookup uses WHERE name = $1 without user_id.
- RiskGateway._runtimeIdToBroker is process-global and keyed only by runtimeId; fallback broker construction does not pass user/account context.
- SocketXServer ownership verification depends on optional accountResolver injection.

Required correction:
- P1-01 and P1-04 define explicit, non-ambiguous tenant ownership fields and enforce them at every lookup, command, subscription, job, artifact and broker/account boundary.
- Never trust client-supplied userId/runtimeId as authorization.
- Define tenant-aware uniqueness, foreign keys and repository query requirements.
- VERIFY WebSocket runtime ownership and whether accountResolver is ever supplied. The actual userScope separator is '::' (not '__'); entity IDs are sanitized but userId is only trimmed, so confirm the allowed userId alphabet/format before concluding delimiter ambiguity. Audit all strategy/report/upload queries and fallback broker construction.
- Multi-user LIVE is blocked until cross-tenant tests cover HTTP, WS, worker, storage and broker routing.

### M2 — MarketFeed crosses domains and lacks per-runtime fault containment

Reviewer evidence:
- MarketFeed lives in market-data but invokes runtime/broker/strategy behavior.
- Global bus listener dispatches async ticks without per-runtime ordering/backpressure.
- Slow runtimes can overlap themselves and delay other runtimes on the same symbol.
- Strategy timeout uses Promise.race with an uncleared timer and does not cancel underlying work.
- Rejected broker results may still cause SIGNAL_EXECUTED emission.
- Errors outside inner try/catch can escape as unhandled rejections; index.js reportedly shuts down on unhandled rejection.

Required correction:
- Market-data owns ingestion, normalization and feed subscriptions; trading runtime owns dispatch, ordering, strategy invocation and broker interaction.
- Prefer direct per-runtime subscription/queue with bounded capacity, explicit overflow policy, ordering guarantees and independent failure handling. Events remain useful for UI fan-out, not implicit execution call graphs.
- Define a fault domain per runtime: one bad strategy must not crash or stall other users/runtimes.
- Define real cancellation/termination semantics; Promise.race alone is not cancellation.
- Emit success events only after confirmed accepted/executed outcomes; represent rejected/failed outcomes separately.
- Verify outer exception paths, engine shutdown policy and event consumers before changing implementation.

### M3 — Job state, cancellation, retry and recovery

Reviewer source findings, to be independently checked before code changes:
- Cancel clears locked_by, while worker progress writes require the worker lock; progress may remain RUNNING although job endpoint says cancelled.
- Queued cancellation is not terminally reflected in progress.
- shouldAbort is reportedly omitted from resolved simulation config; cancellation is observed only between phases.
- A failed success write is conflated with cancellation, leaving a running job to be requeued after stale timeout.
- Failure persistence and retry scheduling are separate, non-atomic steps.
- Deterministic failures such as validation failures are retried.
- SIGTERM closes DB/exits without aborting or releasing the running job.
- A synchronous infinite loop can block heartbeat and trigger duplicate execution after stale requeue.

Required correction:
- P0-05/P1-04 define one authoritative job state machine, terminal-state authority, atomic claim/complete/fail/retry transitions, cancellation ownership, worker lease/heartbeat, shutdown, idempotency and stale-worker fencing.
- Progress, status and report APIs derive from the same authoritative state.
- Distinguish cancellation, persistence failure, transient infrastructure failure and deterministic input/strategy failure.
- Define retry classification and bounded attempts; deterministic validation/compilation errors must not be blindly retried.
- Strategy execution needs enforceable CPU/time/memory termination.
- Test crash points between transitions and prove jobs cannot execute twice or become stranded.

### M4 — Backtest correctness and determinism

Reviewer source findings:
- Controller passes commissionPct, slippageBps, spread, barBudget and batchSize, but config resolution reportedly drops them; BacktestDriver reads commissionPct at a different nesting level.
- Report hardcodes commission/slippage to zero.
- Simulation reportedly fills at signal bar close; next_bar policy exists in another submit path that backtests bypass.
- Gap-through stops reportedly fill at stop price.
- Global trailingStopLossPct reportedly resolves but is never read.
- Async onBar is not awaited and can silently produce zero trades.
- Date-range values are validated but not passed into options, so validation fails after job acceptance.
- Missing OHLC columns become zero; timezone-less dates use server-local parsing.
- No injected clock or seeded RNG; Date.now()/Math.random() make runs non-reproducible.
- Entry accounting deducts full notional while equity adds only unrealized P&L; reviewer flags likely equity understatement.
- barBudgetMs and batchSize are request-controlled and need server-side clamps.

Required correction:
- P1-03 freezes shared portfolio/accounting contract before backtest rebuild.
- P1-03 defines strategy callback contract and async semantics consistently across LIVE/PAPER/BACKTEST (next/onBar/onTick/onMarketData/_processData).
- P1-03 defines fill timing, gap-through behavior, stops/trailing stops, costs, risk policy and mode parity.
- P1-04 defines strict dataset validation, timezone/time-index rules, deterministic clock/RNG injection and reproducible run metadata.
- Server owns resource limits; clamp budgets and batch sizes independently of client input.
- Verify with hand-calculated fixtures and controller/worker tests. Verify BaseBroker/PAPER accounting before declaring the issue universal.

### M5 — Artifact and persistence integrity

Reviewer source findings:
- Report file/CSV/DB writes are non-atomic and errors are swallowed, allowing a succeeded job with no retrievable report.
- Stored report reportedly truncates trades to 20; full trades exist only in local CSV.
- Uploads/reports use process.cwd()/data, incompatible with ephemeral or multi-instance deployment.
- Cleanup operates on shared directories; upload dedup blobs are shared by digest.
- Job UUID, clientJobId and scoped runtime/report ID are separate; CSV URL reportedly retains the scoped ID.
- sanitizeForDb strips non-ASCII characters.
- Performance is computed by both MetricsAccumulator and format.buildReport.

Required correction:
- P1-04 defines canonical IDs, tenant ownership, artifact metadata, storage adapter, retention, cleanup isolation, report completeness, atomic publication and integrity verification.
- Recommended production target: durable object storage behind a storage port; local disk may remain a development adapter. Final provider is an Owen decision.
- Separate private internal IDs from public client-safe IDs; do not embed raw user IDs in public URLs.
- Choose one authoritative performance calculation path.
- Preserve Unicode unless a specific downstream schema requires normalization.
- Verify transaction boundaries, migrations and existing storage behavior.

## 5. Decisions reserved for Owen

| Decision | Recommended default to evaluate | Why it matters |
|---|---|---|
| Strategy isolation and LIVE scope | Do not enable multi-user LIVE until untrusted strategies execute in a killable, least-privilege process/isolate with no ambient DB/secrets/network access | Prevents cross-user compromise and main-process failure |
| Risk and backtest parity | One risk-policy contract and order-intent entry point; backtests use same policy by default with explicit simulation adapters | Avoids modes accepting different unsafe actions |
| Fill timing and costs | Next-bar-open when a signal is produced from a completed bar; explicit commission, spread, slippage and gap rules | Prevents lookahead and unrealistic results |
| Artifact storage | Durable object-storage adapter for production; local disk only for development/single-instance | Supports multi-instance deployment and durable reports |
| Retry policy | Retry only classified transient infrastructure failures; never retry deterministic validation/compile errors | Avoids repeated invalid jobs and confusing status flaps |

Owen may choose different policies, but record each decision with rationale and release gates.
