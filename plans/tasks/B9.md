## 1. Problem

`_attemptRecovery` stops the crashed runtime and restarts it. If a user stop request for the same
strategy lands while the recovery is awaiting `loader.stopStrategy()`, the stop is invisible to the
recovery: the STOPPED it causes is suppressed (it looks like recovery's own stop), and the registry
entry can be gone before recovery looks at it. Recovery then treats "nothing to stop" as success and
restarts the runtime the user asked to stop.

Risk is highest in LIVE mode: an unintended restart of a live runtime.

## 2. Why the existing checks do not cover it

`_attemptRecovery` (`engine/core/engine.js:308-415`) has two cancellation signals:

| Signal | Blind spot |
| --- | --- |
| `!strategyRecoveryStates.has(id)` (record cleared by the STATE_CHANGED listener) | The listener ignores a `STOPPED` while `recoveryStopping` holds the id, so a user stop inside the window does not clear the record. |
| `removedByOther` (stop returned false and the entry is gone) | Needs `entry` to have existed when recovery resolved it. If the user's stop already removed the entry, `entry` is null, `stopResult` is `false` and `removedByOther` is `false` — the restart proceeds. |

Neither signal observes the stop *request*; both infer it from registry/ledger state, which is exactly
what the race removes.

## 3. Approach

Record the request at the loader boundary, where every stop passes through, and let recovery compare a
sequence number across its own await.

1. `engine/strategyLoader.js` owns a monotonic per-runtimeId stop-request counter.
2. `stopStrategy` increments it for every target **before** terminating, unless the caller is the
   recovery loop itself (`options.internal === true`).
3. `_attemptRecovery` reads the counter before its own stop and re-reads it after; a change means a
   user stop landed inside the window, so recovery cancels: no restart, no reschedule, not counted as a
   failed attempt.

The counter is keyed by runtimeId because a strategy-wide stop targets every runtime of the strategy,
including the recovering one.

**In scope**
