# B11 — Cancel recovery when a user stops during startStrategy

**Status:** NEXT — task defined; implementation not started
**Priority:** High — user intent / LIVE runtime safety
**Owner:** Owen (approval); implementation on the existing local CoreX worktree by Kilo when assigned
**Source:** GitHub issue #69; B9 / PR #68 (6d35335)
**Dependencies:** B9 merged; B10 merged. No dependency on the live-bar parity code change, but avoid concurrent writers to the same recovery files.

## 1. Problem

A user stop issued while engine recovery is inside startStrategy can be silently lost. The runtime has not yet registered, so strategy-level stopStrategy(strategyName) resolves no targets, returns false before the B9 runtime-keyed stop marker is reached, and records no cancellation signal. Recovery then completes the start and clears its recovery state. This can restart a LIVE runtime after an explicit user stop.

Issue: https://github.com/ssemandaowen/corex_engine/issues/69

## 2. Required behavior

A user stop request for a strategy must be observable even when no runtime entry or cleanup reservation currently exists. Recovery must not complete or retain a runtime after a user stop that arrived during its restart window.

B9's runtimeId-keyed marker remains in place for the stop-during-recovery-stop window. B11 adds strategy-level intent tracking for the no-target / booting window; do not replace or weaken B9.

## 3. Proposed bounded implementation

- Add a monotonic strategy-keyed user-stop sequence at the loader boundary. A strategy-level stop increments it even when target resolution returns an empty list.
- Keep internal recovery stops from incrementing the user-stop sequence.
- In _attemptRecovery, snapshot the strategy-level sequence before entering startStrategy, then compare it after the await resolves.
- If the sequence changed, cancel recovery and ensure the just-started runtime is stopped/terminated through the existing lifecycle owner. Do not schedule another retry and do not report a normal successful recovery.
- Preserve runtimeId scoping and the existing RuntimeRegistry as the sole runtime owner.
- Ensure the cancellation path is safe if the runtime is still compiling, has just registered, or the stop arrives at the same time as successful start completion. Do not add a second runtime ledger.

The exact cleanup ordering must be checked against startStrategy reservation/registration and RuntimeLifecycle single-flight semantics before editing. If the current loader API cannot safely stop the just-created runtime after the sequence changes, stop and propose the smallest contract adjustment rather than inventing a parallel state store.
