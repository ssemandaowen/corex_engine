## 1. Problem

`strategy_runtimes` (desired runtime state) has **no foreign key** onto `strategies`
(`schema.sql`, no constraint between them). Deleting a strategy therefore left its `ACTIVE` runtime rows
behind, and boot restoration reads exactly those rows:

```text
engine/strategyLoader.js  _restoreDesiredRuntimeStates()
    SELECT ... FROM strategy_runtimes WHERE actual_state = 'ACTIVE'
```

Two consequences, both observed against the live database during the PR #71 audit:

1. Every boot retried a start that can only fail — `Strategy '<id>' not found in DB` — logged a
   warning, and left the orphan `ACTIVE` forever.
2. Re-registering the same name (client save/upload, `npm run strategies:migrate`,
   `engine/services/corex-reg.js` — all name-keyed upserts that recreate the row verbatim) made the
   orphan **start by itself** on the next boot. This is the "deleted strategy reappears" report.

Nothing reconciled desired state against the strategy registry; the restore failure was a warning and
was never acted on. Deletion was also non-atomic: one `DELETE FROM strategies` with no statement for
`strategy_runtimes`.

## 2. Changes

### 2.1 Reconcile before restore (boot cold path)

`engine/strategyLoader.js` — `_reconcileOrphanedRuntimeStates()`, awaited at the top of
`_restoreDesiredRuntimeStates()` before the restore `SELECT`:

```sql
UPDATE strategy_runtimes
   SET actual_state = 'STOPPED', updated_at = NOW()
 WHERE actual_state = 'ACTIVE'
   AND NOT EXISTS (SELECT 1 FROM strategies s WHERE s.name = strategy_runtimes.strategy_name)
RETURNING runtime_id, strategy_name
```

- Orphan rows only. A row whose strategy exists is never modified, so valid runtimes of any user are
  untouched. One statement, no per-row query.
- Marked `STOPPED`, which restore already ignores — the smallest change that ends the retry loop
  without deleting history. No schema change: there is no metadata column to record the reason, so the
  reason is logged (`[RESTORE] Reconciled N orphaned desired-state row(s) ...`) rather than stored.
- A reconciliation failure is logged and never blocks restoration: the worst case is the previous
  behaviour (one failed restore attempt per orphan).

### 2.2 Atomic delete

`engine/routes/strategyController.js` — `DELETE /:id` runs both statements in one
`db.withTransaction` callback (`engine/services/postgres.js:71-85`: one pooled client, `BEGIN`,
`COMMIT`/`ROLLBACK`, `release()` in `finally`):

```text
DELETE FROM strategies         WHERE name = $1
DELETE FROM strategy_runtimes  WHERE strategy_name = $1
```

- A missing strategy throws a sentinel **inside** the transaction, so nothing commits and the route
  still answers `404 Strategy not found`.
- The success audit line reports how many runtime records were removed.
- Authorization/ownership checks, the deletion claim and the strategy-version cascade are unchanged.

### 2.3 A start in flight blocks the delete

Found during review of PR #72 (not in the original B10 scope). A start reserves its runtime identity
only *after* the strategy `SELECT` and the compile (`strategyLoader.js` `startStrategy`), so between
those points the registry has no entry, no reservation, and the ledger is not yet `ACTIVE`. The delete
gate saw an idle strategy, a delete could commit mid-compile, and the start would then boot a runtime
against a strategy row that no longer exists — database consistent, live instance orphaned.

- `engine/strategyLoader.js` exposes `isStartInFlight(id)` over the existing `_startInFlight` set
  (cleared in a `finally`, so it cannot stick).
- `engine/core/loader/StrategyLoader.js` exposes it on the facade.
- The `DELETE` gate refuses (`403 Cannot delete while strategy is active`) while it is true.

Refusal, not termination, is the intended semantics: stopping execution and deleting a strategy are
separate operations, and a DELETE must never stop live trading (Owen's decision).
